### 막힌 것 (트러블슈팅)

**1. `@WebMvcTest`를 잘못 진단해서 승인된 파일을 무단으로 되돌림**
→ 증상: GlobalExceptionHandler 테스트 작성 중 `org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest`를 찾을 수 없다는 컴파일 에러
→ 원인(잘못된 진단): 서브에이전트가 "Spring Boot 4.1.1엔 `@WebMvcTest`가 없다"고 판단하고 이미 리뷰 승인된 `api/build.gradle`(테스트 의존성)과 `ApiResponse.java`(불필요한 `@JsonProperty` 추가)를 무단으로 수정
→ 실제 원인: `@WebMvcTest`는 존재하지만 패키지가 `org.springframework.boot.webmvc.test.autoconfigure`로 이동했을 뿐 (Maven Central POM + 캐시된 jar 직접 확인으로 검증)
→ 해결: 무단 변경 원복 + import 경로만 수정

**2. 같은 원인으로 `@DataJpaTest`, `@AutoConfigureMockMvc`, `TestEntityManager`도 패키지 이동**
→ 증상: 아직 실행 전이지만, 1번과 같은 문제가 hub 도메인 계획에도 잠재해 있었음
→ 원인: Spring Boot 4.1.1이 테스트 슬라이스 어노테이션들을 모듈별로 재배치 (`@DataJpaTest` → `org.springframework.boot.data.jpa.test.autoconfigure`, `TestEntityManager` → `org.springframework.boot.jpa.test.autoconfigure`, `@AutoConfigureMockMvc` → `org.springframework.boot.webmvc.test.autoconfigure`)
→ 해결: 실행 전에 캐시된 jar 내용을 직접 확인해서 hub 도메인 계획 문서의 import를 미리 수정해둠

**3. `ApiKeyAuthFilter` 추가 후 이전에 통과하던 테스트가 401로 깨짐**
→ 증상: 전체 빌드(`./gradlew build`)를 돌리니 `GlobalExceptionHandlerTest`가 404 기대했는데 401 응답
→ 원인: `@Component`로 등록된 `Filter`는 `@WebMvcTest` 슬라이스에도 기본 포함되는데, 이 테스트는 `X-API-KEY` 헤더를 안 보내서 인증 필터에 먼저 막힘 — 각 태스크를 개별 리뷰할 때는 안 보였고 전체 빌드를 돌려야만 드러나는 교차 태스크 버그였음
→ 해결: `@AutoConfigureMockMvc(addFilters = false)` 추가. hub 도메인 계획의 컨트롤러 테스트에도 미리 반영
→ 교훈: 태스크 단위 리뷰만으로는 부족하고, 매 태스크 뒤 전체 빌드를 돌려야 이런 상호작용 버그를 잡을 수 있음

**4. `@DataJpaTest`가 JPA Auditing을 안 태움 (최종 리뷰에서 발견, 실행 전에 미리 수정)**
→ 원인: `@DataJpaTest`의 타입 제외 필터가 평범한 `@Configuration`인 `JpaAuditingConfig`를 슬라이스에서 걸러냄
→ 해결: hub 도메인 계획의 모든 `@DataJpaTest`에 `@Import(JpaAuditingConfig.class)` 추가하고 Global Constraints에 규칙으로 명시

**5. Gradle wrapper(`gradlew`, `gradle/wrapper/*`)가 생성만 되고 커밋 안 됨**
→ 증상: 로컬에선 빌드가 되는데, 이 상태로 다른 사람이 브랜치를 받으면 `./gradlew`부터 실행이 안 됐을 것
→ 해결: wrapper 파일들을 커밋하고 루트 `.gitignore`에 `build/`, `.gradle/` 등 추가

**6. 컨트롤러(나)와 서브에이전트가 같은 워킹 디렉토리에서 동시에 git 작업 → 커밋 하나에 섞임**
→ 증상: 서브에이전트가 커밋하려던 시점에 컨트롤러가 이미 다른 파일을 커밋해버려서, 서로 다른 두 작업이 커밋 하나에 같이 들어감
→ 원인: 이 계획을 격리된 git worktree 없이 메인 체크아웃에서 바로 실행함
→ 영향: 기능적으로는 문제없었음(둘 다 올바른 변경) — 다음부터는 worktree로 격리하는 게 안전

**7. AI가 레포 전체 구조를 처음부터 잘못 잡음 (사용자가 직접 캐치)**
→ 증상: 스캐폴딩을 레포 루트에 바로 만듦 (`build.gradle`, `settings.gradle`, `common/`, `api/`가 레포 최상위)
→ 문제: 사용자가 "client, 파이프라인, 다른 포지션 폴더도 같은 git에 올릴 것"이라고 알려주기 전까지 AI는 이 레포가 백엔드 전용이라고 가정하고 설계함 — 사용자의 실제 계획(모노레포)을 미리 묻지 않은 게 원인
→ 해결: 사용자가 문제를 지적한 뒤, 백엔드 전체(Gradle 멀티모듈 + `docs/superpowers/`)를 `server/` 하위로 재배치. 기존 이슈 #1 스캐폴딩은 삭제하고 같은 `server/` 이름을 새 구조가 이어받음
→ 교훈: "이 프로젝트 하나만 있는 레포"라고 넘겨짚지 말고, 레포에 다른 것도 같이 올라갈 계획인지 구조 설계 전에 먼저 물어봤어야 함

**8. 로컬 작업 디렉토리 이름에 밑줄(`backend_Project`) 사용 — 사용자가 컨벤션 통일 요청**
→ 요청: `backend_Project` → `backend-project`로 변경 (다른 프로젝트들도 같은 상위 폴더 아래 git 연결돼 있음)
→ 처리: 이름 변경 전에 하위 레포들(`HubDash`, `WAP_Project/Plitter-BE`)에 git worktree나 로컬 파일 경로를 참조하는 원격(remote)이 있는지 먼저 확인 (worktree 없음, 원격 전부 HTTPS) → 안전 확인 후 디렉토리 이름 변경, 두 레포 모두 정상 동작 확인

### AI 도움 받은 부분 (기록용)
이번 세션은 전 과정에서 Claude Code(AI)의 도움을 받아 진행함 — 특히 위 트러블슈팅 1~6번(Spring Boot 버전 관련 버그 진단, 교차 태스크 버그 발견)은 AI가 서브에이전트를 통해 구현하고 스스로 리뷰/재검토하며 잡아낸 것이고, 7~8번(레포 구조/디렉토리 이름 문제)은 사용자가 직접 짚어준 걸 AI가 안전성 확인 후 실행한 것. AI가 놓친 부분(7번)과 AI가 잡아낸 부분(1~4번)을 구분해서 기록해둠.

### 배운 것
- Spring Boot 4.1.1은 테스트 슬라이스 어노테이션(`@WebMvcTest`, `@DataJpaTest` 등)을 기능별 모듈로 재배치했다 — "클래스를 못 찾겠다"는 에러가 "기능이 없다"를 의미하지 않을 수 있으니, 반전/재작성보다 먼저 실제 jar를 확인하는 습관이 필요
- `@Component implements Filter`는 `@WebMvcTest`에도 기본 포함된다 — 인증 필터를 넣은 뒤로는 관련 없는 슬라이스 테스트에도 `addFilters = false`가 필요해짐
- 태스크별 리뷰는 각 diff만 보기 때문에, 서로 다른 태스크가 상호작용해서 생기는 버그(3번)는 전체 빌드를 직접 돌려봐야만 잡힌다
- 레포에 여러 스택(백엔드/클라이언트/파이프라인)을 같이 올릴 계획이면, 처음부터 각 스택을 하위 폴더로 격리해두는 게 나중에 옮기는 것보다 훨씬 싸다
- 구조 설계 전에 "이 레포에 다른 것도 올라올 계획인가"를 먼저 물어봤어야 했다 — 사용자가 나중에 알려줘서 재작업이 생김 (트러블슈팅 7번)
