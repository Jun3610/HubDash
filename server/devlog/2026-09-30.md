### 막힌 것
- 새로 만든 테스트를 넣자 기존 테스트 수십 개가 컨텍스트 로딩 실패
→ 원인: `NotionClient`, `CalDavClient`에 테스트용 생성자(RestClient.Builder 주입)를 추가해 생성자가 둘이 됐는데, 스프링이 쓸 생성자를 지정하지 않음
→ 해결: 공개 생성자에 `@Autowired`
- CalDAV 캘린더 이름 "집"이 "ì§\u0091"로 깨짐
→ 원인: 응답을 문자열로 받았는데 Content-Type에 charset이 없으면 ISO-8859-1로 읽힘
→ 해결: 바이트로 받아 XML 파서가 XML 선언(없으면 UTF-8)으로 읽게 함
- 스프링 기본 HTTP 엔진(HttpURLConnection)은 `PROPFIND`/`REPORT`를 보내지 못함
→ 해결: CalDAV만 JDK HttpClient(`JdkClientHttpRequestFactory`)를 명시
- 전체 테스트에서 저장소 테스트 6개가 `Table ... not found`로 실패(#139의 그 증상이 더 넓게)
→ 원인: 모든 테스트 컨텍스트가 같은 이름의 인메모리 H2(`testdb`)를 공유. 테스트 컨텍스트 캐시에서 밀려난 컨텍스트가 닫히며 `create-drop`으로 테이블을 지우면, 같은 DB를 쓰던 다른 컨텍스트의 테스트가 실패. 설정이 다른 테스트 컨텍스트를 둘 추가하자 더 자주 터짐
→ 해결: `jdbc:h2:mem:testdb-${random.uuid}`로 컨텍스트마다 다른 DB

### 배운 것
- 비밀값은 "어디에 남을 수 있나"를 따라가며 막아야 한다 — 응답(마스킹), DB(암호문), 설정 JSON(비밀 제외), 예외 메시지(토큰 미포함), 요청 객체의 toString(앱 암호 제외)
- 저장 전 검증은 "키가 있는지 → 입력 형식 → 외부 로그인" 순서로, 싸고 확실한 것부터 해야 외부 호출을 낭비하지 않는다
- 불안정한 테스트는 "가끔 실패"로 두지 말고 무엇이 공유되는지(여기서는 인메모리 DB 이름)를 찾으면 한 줄로 고쳐지는 경우가 많다
