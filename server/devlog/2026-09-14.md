### 배운 것
- Spring Boot DevTools가 켜진 상태로 `bootRun` 중이면, 별도 재시작 없이 `./gradlew build`만 다시 돌려도 클래스 변경이 자동 반영된다(재시작 로그의 `restartedMain`, 동일 프로세스에서 `process running for Xs`로 확인 가능) — 매번 서버를 새로 안 띄워도 수정-재검증 루프를 빠르게 돌릴 수 있음
- 인증 필터만 잘 동작한다고 API가 다 잘 동작하는 게 아니다 — 필터를 통과한 뒤의 공통 예외 처리 경로(404/500)도 별도로 확인해야 실제로 "모든 응답이 통일된 포맷"이라는 설계 원칙이 지켜지는지 알 수 있다
- Spring 프레임워크 클래스의 생성자/시그니처도 버전 간에 바뀔 수 있다 — 컴파일 에러가 나면 추측하지 말고 실제 jar/소스를 까서 확인하는 습관이 필요 (이전 세션의 "패키지 이동" 교훈과 같은 계열)

### 막힌 것
- `docker compose up` + `bootRun`으로 실제 Postgres에 기동하니 `SchemaManagementException: missing table [hub_category]` — Flyway 마이그레이션이 전혀 실행 안 됨 (H2 기반 자동 테스트로는 절대 못 잡는 종류의 버그)
→ 원인: Spring Boot 4.1.1에서 `FlywayAutoConfiguration`이 모놀리식 `spring-boot-autoconfigure` jar에서 분리되어 별도 모듈 `spring-boot-flyway`로 이동함. api/build.gradle에는 Flyway 벤더 라이브러리(`flyway-database-postgresql`)만 있고 이 자동설정을 켜는 `spring-boot-starter-flyway`가 빠져있어서 클래스패스에 `FlywayAutoConfiguration` 자체가 없었음(--debug condition evaluation report에도 전혀 안 나옴)
→ 해결: `spring-boot-flyway` jar를 직접 까서 `FlywayAutoConfiguration` 위치 확인, `spring-boot-starter-flyway` 의존성 추가
- 서브에이전트가 익숙하지 않은 패키지 경로 에러를 보고 "의존성이 없다"고 오판해서 불필요한 의존성을 추가/삭제하는 패턴이 두 번 더 반복됨(HubCategoryControllerTest의 Jackson 2/3, Task 9 통합 테스트의 spring-boot-jpa-test 중복 추가)
→ 원인: 이 프로젝트의 Spring Boot 4.1.1이 Jackson 3(`tools.jackson.*`)과 다수의 분리된 테스트 스타터(webmvc-test, data-jpa-test 등)를 쓰는데, 이게 익숙하지 않으면 "클래스를 못 찾음 = 의존성 누락"으로 성급히 결론 내리기 쉬움
→ 해결: 실제 Gradle Module Metadata/의존성 트리를 까서 확인하는 걸 원칙으로 삼음. 리뷰 단계에서 매번 잡아내고 되돌림
- 최종 리뷰에서 `PUT /api/hub/links/{id}`가 필수(`@NotNull`) 필드인 categoryId를 받고도 조용히 무시하던 실버그 발견 (카테고리 이동이 항상 무시되고 200 OK로 응답)
→ 원인: `HubLinkService.update()`가 title/url/description만 반영하고 categoryId는 아예 안 씀
→ 해결: `hubCategoryRepository.findById(categoryId)`로 새 카테고리 조회 후 `HubLink.changeCategory()` 추가해서 반영. ArgumentCaptor로 실제 카테고리가 바뀌었는지 검증하는 테스트 추가

### 배운 것
- H2 기반 자동 테스트 프로파일(`spring.flyway.enabled=false`)은 구조적으로 "Flyway가 실제로 동작하는지"를 검증할 수 없다 — 이번처럼 스키마 자동설정 자체가 빠진 버그는 오직 실제 Postgres에 띄워보는 수동 검증으로만 잡힌다. 사용자가 요청한 "docker 띄워서 확인" 단계가 자동화 테스트의 사각지대를 정확히 메워줌
- Spring Boot 4.1.1은 이 프로젝트에서 Jackson, WebMvc/JPA 테스트뿐 아니라 Flyway 자동설정까지 별도 -starter- 아티팩트로 쪼개놓았다 — 벤더 라이브러리를 추가했다고 Spring Boot 자동설정까지 따라오는 게 아님. 새 인프라 의존성을 추가할 때는 대응하는 -starter- 모듈이 별도로 있는지부터 확인하는 습관 필요
- 필수(`@NotNull`) 요청 필드를 받고도 서비스 로직에서 실제로 안 쓰면, 컴파일도 되고 200으로 응답도 하는 "조용한 무시" 버그가 생긴다 — DTO에 필드를 넣을 땐 그 필드가 서비스 로직 전체 경로(특히 update류)에서 실제로 소비되는지 끝까지 추적해야 함
