### 막힌 것
- 로컬 Docker 데몬이 꺼져있어 `docker compose up` 최초 실행 실패
→ 원인: Docker Desktop 앱이 실행 안 된 상태
→ 해결: `open -a Docker`로 앱 실행 후 `docker info`로 데몬 준비될 때까지 폴링
- 인증 필터 통과 후 매칭되는 컨트롤러가 없거나(404) 예외가 처리 안 되면(500) Spring Boot 기본 에러 응답(스택트레이스 포함)이 그대로 나감 — 프로젝트 원칙(모든 응답 ApiResponse로 통일)과 어긋남
→ 원인: GlobalExceptionHandler가 EntityNotFoundException, MethodArgumentNotValidException만 처리하고 있었음
→ 해결: NoResourceFoundException(404)과 Exception catch-all(500) 핸들러 추가, TDD로 테스트 먼저 작성 후 구현 (이슈 #10)
- 테스트 코드에서 `NoResourceFoundException` 생성자 시그니처가 Spring 7에서 `(HttpMethod, resourcePath)` 2개가 아니라 `(HttpMethod, requestUri, resourcePath)` 3개로 바뀌어 컴파일 에러
→ 원인: Spring 6.1에서 추가된 클래스가 이후 버전에서 시그니처 변경됨 (spring-webmvc 7.0.9 소스로 직접 확인)
→ 해결: 3-인자 생성자로 수정, 체크 예외라 메서드에 throws 선언 추가

### 배운 것
- Spring Boot DevTools가 켜진 상태로 `bootRun` 중이면, 별도 재시작 없이 `./gradlew build`만 다시 돌려도 클래스 변경이 자동 반영된다(재시작 로그의 `restartedMain`, 동일 프로세스에서 `process running for Xs`로 확인 가능) — 매번 서버를 새로 안 띄워도 수정-재검증 루프를 빠르게 돌릴 수 있음
- 인증 필터만 잘 동작한다고 API가 다 잘 동작하는 게 아니다 — 필터를 통과한 뒤의 공통 예외 처리 경로(404/500)도 별도로 확인해야 실제로 "모든 응답이 통일된 포맷"이라는 설계 원칙이 지켜지는지 알 수 있다
- Spring 프레임워크 클래스의 생성자/시그니처도 버전 간에 바뀔 수 있다 — 컴파일 에러가 나면 추측하지 말고 실제 jar/소스를 까서 확인하는 습관이 필요 (이전 세션의 "패키지 이동" 교훈과 같은 계열)
