### 막힌 것
- 스케줄러 테스트 5개가 `UnfinishedStubbingException` — `when(runner.run(...)).thenReturn(execution(...))`에서 `execution()`이 안쪽에서 `when()`을 다시 호출해 바깥 스터빙이 끝나기 전에 끼어듦 → 목 객체를 먼저 변수로 만든 뒤 스터빙. 일괄 치환하다 변수명이 상태와 반대(COMPLETED 실행이 `failed`)로 뒤바뀐 걸 발견해 정정
- `WeeklyStatJobRunner`에 생성자가 둘(공개 + 테스트용 Clock 주입)이라 이슈 #56에서 겪은 "No default constructor found"를 피하려고 공개 생성자에 처음부터 `@Autowired`를 명시 — 같은 실수를 반복하지 않음

### 배운 것
- 라이브러리가 실패를 예외가 아니라 반환값 상태로 알려줄 때 반환값을 버리면 실패가 조용해짐 — try/catch가 있어도 안전하지 않음. 이슈 본문의 진단만 믿지 않고 코드를 확인해서 더 큰 문제를 찾음
- 지금까지 모든 배치 검증이 수동 엔드포인트만 거쳤고 스케줄 경로는 한 번도 실환경에서 돌려본 적이 없었음 — cron을 프로퍼티로 빼두면 짧은 주기로 실제 스케줄을 검증할 수 있음
- 멱등한 작업은 재시도 로직을 만들기보다 주기적으로 다시 돌리는 편이 더 단순하고 견고함
- 관찰: 실패 로그의 원인이 `FatalStepExecutionException: Unable to process chunk`까지만 나오고 근본 원인(SQL 오류)은 Spring Batch 자체 로그의 스택트레이스에 있음 — 필요하면 근본 원인을 한 줄에 함께 남기도록 개선 가능
