## 2026-09-19 (이어서, 주간 집계 배치를 pknu 도메인으로 확장 — 이슈 #62)
### 한 일
- health(#61, PR #64) 머지 직후 이어서 pknu(Assignment) 진행 — 이걸로 이슈 #58의 하위 이슈 3개(study/health/pknu)가 전부 완료됨
- `AssignmentWeeklyStat`(주간 총 과제 수/완료 수, `dueDate` 기준) + Flyway V22, `analytics/pknu`(Job/Step/Reader/Processor/Writer, BatchService), 컨트롤러(GET 조회 + POST 수동 배치 트리거), 스케줄러 등록
- Reader는 대상 주에 마감인 과제가 있는 courseId만 선별, 응답에는 파생값 `completionRate`(완료 수/총 수)를 포함(저장은 카운트만)
- `./gradlew :api:test` 223개 전체 통과. 실제 docker+bootRun에서 코스1(대상 주 3건 중 2건 완료, 주 밖 2건 제외) → `3/2`, 코스2 → `1/0`, 과제 완료 처리+추가 후 재실행 시 같은 행이 `4/3`(completionRate 0.75)로 갱신, 마감 과제 없는 주는 행 미생성을 curl과 `psql`로 확인

### 막힌 것
- 실환경 검증 첫 시도에서 코스 생성 요청이 전부 400이라, 배치는 COMPLETED인데 통계 행은 0건이었음
→ 원인: 시드 요청에 `credits`로 잘못 보냄(실제 필드명은 `credit`) — 기능 버그가 아니라 검증 데이터 오류. 코스가 없으니 배치가 빈 Reader로 정상 종료해 "성공"처럼 보였음
→ 해결: 필드명 수정 후 재시드·재검증

### 배운 것
- 배치가 COMPLETED여도 처리 대상이 0건이면 아무것도 검증되지 않은 것 — 기대 집계값(total/completed)을 먼저 적어두고 실제 DB 행과 대조해야 함
- 새 도메인을 이 패턴으로 복제할 때 sed 치환은 대소문자 변형(`findByTopicId` vs `topicId`)을 놓치기 쉬움 — 치환 후 원본 도메인 용어가 남았는지 grep으로 확인해야 함

## 2026-09-19 (이어서, FatSecret API 클라이언트 연동 — 이슈 #56)
### 한 일
- 이슈 #58 완료 후 남은 작업 중 FatSecret 연동(#56)에 착수. 코드보다 먼저 실제 API를 curl로 호출해 응답/에러 형태를 확인: 토큰 발급은 성공(`expires_in=86400`), 검색/조회는 전부 `error code 21: Invalid IP address detected`, 잘못된 토큰은 code 13(둘 다 HTTP 200 + 본문 error), 잘못된 자격증명은 HTTP 400 `invalid_client`
- `FatSecretTokenProvider`(토큰 발급/캐싱, 만료 60초 전 갱신, 거부 시 재발급), `FatSecretClient`(foods.search/food.get.v4, 토큰 거부 시 1회 재시도, 결과 1건이면 배열 대신 객체로 오는 FatSecret JSON 특성 처리), `FoodController`(`GET /api/health/foods/search`, `GET /api/health/foods/{foodId}`) 구현
- 연동 지점은 "조회 전용"으로 설계 — 응답 영양 필드를 `MealRecordRequest`와 같은 이름/단위로 맞춰, 클라이언트가 serving을 골라 기존 식사 기록 생성 API에 그대로 옮기게 함(식사 기록을 서버가 자동 생성하지는 않음)
- 실패를 유형별로 구분(키 없음 503 / 인증 실패·IP 미허용·업스트림 오류 502 / 한도 초과 429)하고, 파라미터 제약 위반이 500이 되던 것을 400으로 처리하도록 `HandlerMethodValidationException` 핸들러 추가
- `./gradlew :api:test` 258개 전체 통과(신규 35개). 실제 docker+bootRun으로 실키(IP 미허용 502 + 사용자용 안내 메시지 확인), 잘못된 키(502 AUTH_FAILED), 키 없음(503, 앱 기동·다른 API 정상), 잘못된 파라미터(400 5종), API 키 누락(401)을 직접 확인

### 막힌 것
- 실제 성공 응답을 확인할 수 없음 — FatSecret이 서버 IP(`1.228.64.22`)를 허용 목록에서 거부(code 21). 계정 설정(IP 등록)이라 코드로 풀 수 없는 외부 차단
→ 원인: FatSecret basic scope는 사전에 등록된 IP에서만 API 호출을 허용
→ 해결(미완): 성공 응답 매핑은 문서/기억 기반 형태로 목 테스트만 했고, 실서버 검증은 IP 등록 후 재실행하도록 PR을 머지하지 않고 열어둠. 집 IP가 유동일 수 있어 배포 환경(K3s)에서는 고정 IP가 필요할 수 있음
- 앱 컨텍스트가 뜨지 않아 87개 테스트가 연쇄 실패(`DashboardApplicationTests`, 모든 `@DataJpaTest` 등)
→ 원인: `FatSecretTokenProvider`에 생성자가 둘(공개 + 테스트용 Clock 주입)이라 스프링이 `No default constructor found`로 빈 생성 실패. 단위 테스트는 테스트용 생성자를 직접 호출해서 통과했고 전체 스위트에서야 드러남
→ 해결: 공개 생성자에 `@Autowired` 명시. 처음에는 "테스트 컨텍스트 캐시(32개) 초과로 공유 H2가 drop된 것"이라고 추측했으나, 가장 먼저 실행된 테스트(`DashboardApplicationTests`)의 실패 원인을 열어보니 바로 진짜 원인이 나와서 가설을 버림
- 검색어 특수문자(`&`, `=`) 인코딩 테스트가 실패 — 코드가 아니라 테스트 기대값 문제. `MockRestServiceServer.queryParam` 매처는 디코딩 전 원본을 비교하므로 `mac%20%26%20cheese%3D1`이 정상(오히려 인코딩이 제대로 된 증거)

### 배운 것
- 연쇄 실패는 마지막 실패가 아니라 가장 먼저 실패한 것의 원인을 봐야 한다 — 그럴듯한 가설을 세우기 전에 첫 실패 로그부터 열어볼 것
- 테스트 편의용 두 번째 생성자는 프로덕션 빈 생성을 깨뜨릴 수 있고, 그걸 잡는 건 컨텍스트를 띄우는 테스트뿐 — 단위 테스트만 통과했다고 끝내면 안 됨
- 외부 API는 문서나 기억이 아니라 실제 호출로 에러 형태를 먼저 확인하고 설계해야 한다 — "실패도 HTTP 200으로 온다"는 사실을 알았기 때문에 HTTP 상태만 보는 클라이언트를 만들지 않았음
- 실환경 검증이 외부 요인으로 막혔을 때는 "검증했다"고 뭉뚱그리지 않고, 검증된 것(인증, 실패 경로 전부)과 못한 것(성공 응답 매핑)을 분리해서 남겨야 함
