## 2026-09-19 (이어서, 주간 집계 배치를 pknu 도메인으로 확장 — 이슈 #62)
### 한 일
- health(#61, PR #64) 머지 직후 이어서 pknu(Assignment) 진행 — 이걸로 이슈 #58의 하위 이슈 3개(study/health/pknu)가 전부 완료됨
- `AssignmentWeeklyStat`(주간 총 과제 수/완료 수, `dueDate` 기준) + Flyway V22, `analytics/pknu`(Job/Step/Reader/Processor/Writer, BatchService), 컨트롤러(GET 조회 + POST 수동 배치 트리거), 스케줄러 등록
- Reader는 대상 주에 마감인 과제가 있는 courseId만 선별, 응답에는 파생값 `completionRate`(완료 수/총 수)를 포함(저장은 카운트만)
- `./gradlew :api:test` 223개 전체 통과. 실제 docker+bootRun에서 코스1(대상 주 3건 중 2건 완료, 주 밖 2건 제외) → `3/2`, 코스2 → `1/0`, 과제 완료 처리+추가 후 재실행 시 같은 행이 `4/3`(completionRate 0.75)로 갱신, 마감 과제 없는 주는 행 미생성을 curl과 `psql`로 확인

### 막힌 것
- 실환경 검증 첫 시도에서 코스 생성 요청이 전부 400이라, 배치는 COMPLETED인데 통계 행은 0건이었음
→ 원인: 시드 요청에 `credits`로 잘못 보냄(실제 필드명은 `credit`) — 기능 버그가 아니라 검증 데이터 오류. 코스가 없으니 배치가 빈 Reader로 정상 종료해 "성공"처럼 보였음
→ 해결: 필드명 수정 후 재시드·재검증

### 배운 것
- 배치가 COMPLETED여도 처리 대상이 0건이면 아무것도 검증되지 않은 것 — 기대 집계값(total/completed)을 먼저 적어두고 실제 DB 행과 대조해야 함
- 새 도메인을 이 패턴으로 복제할 때 sed 치환은 대소문자 변형(`findByTopicId` vs `topicId`)을 놓치기 쉬움 — 치환 후 원본 도메인 용어가 남았는지 grep으로 확인해야 함

- 대신 식사 기록을 "끼니별로 음식을 직접 입력해 하루 합계를 보는" 방식으로 개편(이슈 #69): `MealItem`(음식 한 개) 신설, `MealRecord`는 한 끼만 표현, 영양 합계는 항목의 합으로 계산해 응답에 포함, `GET /api/health/meal-records/daily-summary?date=`로 하루 총합과 끼니별 합계 제공
- Flyway V23으로 기존 끼니의 영양 값을 항목 1건('기존 기록')으로 옮겨 데이터를 보존한 뒤 옛 컬럼을 제거. 하루 합계를 나중에 주간 통계 배치로 넘기는 작업은 이슈 #70으로 분리
- `./gradlew :api:test :common:test` 273개 전체 통과. 실제 docker로 옛 코드(V22)에 예전 방식 데이터를 넣고 새 코드(V23)로 올려 데이터 보존을 psql로 확인한 뒤, 하루(아침 밥+계란, 점심 신라면+김치, 간식 2회) 입력 → 합계(1210kcal, 탄187/단35.3/지33.4, 나트륨2110) 기대값과 일치, 항목 이동/삭제, 끼니 삭제 시 항목 연쇄 삭제, 실패 경로(404, 400) 확인

### 막힌 것
- FatSecret 브랜치의 미커밋 변경을 두고 잘못 보고함 — 사용자가 도구 실행을 거부해서 "아무것도 실행되지 않았고 파일도 그대로"라고 말했는데, 실제로는 명령 안의 파일 수정 스크립트는 이미 실행되었고(테스트 실행만 중단), `git checkout main`이 "local changes would be overwritten"으로 실패하고서야 발견
→ 원인: 거부/중단된 명령이 어디까지 실행됐는지 확인하지 않고 추측으로 보고함
→ 해결: `git status`/`git diff --stat`로 실제 상태를 확인해 정정 보고하고, 삭제하지 않고 "미검증"이라고 명시해 폐기 브랜치에 커밋해 보존
- 마이그레이션 검증 스크립트에서 `exit 1`이 떴으나 `grep`이 잔재(habit)를 못 찾아서 난 정상 종료 코드였음 — 명령을 묶어 실행할 때 마지막 grep의 종료 코드가 전체 실패처럼 보일 수 있음

### 배운 것
- 중단·거부된 작업의 상태는 기억이 아니라 `git status`로 확인해야 함. "아무 일도 안 일어났다"는 가장 위험한 추측
- 컬럼을 제거하는 마이그레이션은 빈 DB 테스트만으로는 데이터 보존이 증명되지 않음 — 옛 버전을 먼저 띄워 데이터를 넣고 새 버전으로 올려야 함(git worktree로 main을 따로 띄우면 브랜치 전환 없이 가능)
- 외부 서비스 도입 전 실제 데이터 커버리지(한국 식품)를 먼저 조사했다면 클라이언트 구현 전에 방향을 정할 수 있었음 — 다음 외부 연동은 "코드 전에 실제 호출로 요구 사항 충족 여부부터" 확인
