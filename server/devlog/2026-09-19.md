### 막힌 것
- FatSecret 브랜치의 미커밋 변경을 두고 잘못 보고함 — 사용자가 도구 실행을 거부해서 "아무것도 실행되지 않았고 파일도 그대로"라고 말했는데, 실제로는 명령 안의 파일 수정 스크립트는 이미 실행되었고(테스트 실행만 중단), `git checkout main`이 "local changes would be overwritten"으로 실패하고서야 발견
→ 원인: 거부/중단된 명령이 어디까지 실행됐는지 확인하지 않고 추측으로 보고함
→ 해결: `git status`/`git diff --stat`로 실제 상태를 확인해 정정 보고하고, 삭제하지 않고 "미검증"이라고 명시해 폐기 브랜치에 커밋해 보존
- 마이그레이션 검증 스크립트에서 `exit 1`이 떴으나 `grep`이 잔재(habit)를 못 찾아서 난 정상 종료 코드였음 — 명령을 묶어 실행할 때 마지막 grep의 종료 코드가 전체 실패처럼 보일 수 있음

### 배운 것
- 중단·거부된 작업의 상태는 기억이 아니라 `git status`로 확인해야 함. "아무 일도 안 일어났다"는 가장 위험한 추측
- 컬럼을 제거하는 마이그레이션은 빈 DB 테스트만으로는 데이터 보존이 증명되지 않음 — 옛 버전을 먼저 띄워 데이터를 넣고 새 버전으로 올려야 함(git worktree로 main을 따로 띄우면 브랜치 전환 없이 가능)
- 외부 서비스 도입 전 실제 데이터 커버리지(한국 식품)를 먼저 조사했다면 클라이언트 구현 전에 방향을 정할 수 있었음 — 다음 외부 연동은 "코드 전에 실제 호출로 요구 사항 충족 여부부터" 확인

- `./gradlew :api:test :common:test` 278개 전체 통과. 실제 docker로 한 주치 식사를 API로 입력해 손계산 기대값(2일, 1200/80/51/62.5)과 일치, 화요일 추가 후 재실행 시 같은 행이 `3일, 1000/86.67/40.67/45`로 갱신, 주 밖 9000kcal 항목 2개와 음식 없는 금요일 끼니가 평균을 오염시키지 않음을 psql로 확인

### 막힌 것
- 테스트 컴파일 오류 — `launchJob`이 체크 예외를 던지는데 테스트 메서드에 `throws Exception`을 빠뜨림(다른 도메인 테스트에서 복사할 때 메서드 시그니처를 새로 썼기 때문). 수정 후 통과. 컴파일 실패 상태에서 집계한 "273개 통과"는 이전 실행의 남은 결과 파일이라 무효였고, 결과 디렉터리를 지우고 다시 돌려 확인함

### 배운 것
- Reader는 청크 트랜잭션 밖에서 생성되어 지연 로딩 컬렉션(끼니의 items)을 못 읽음 — "기록이 있는가"는 count 쿼리로 판단하고 실제 집계는 트랜잭션 안인 Processor에서 함
- 테스트 결과 파일은 빌드가 실패해도 이전 것이 남아 있어, 결과 집계 스크립트가 "통과"로 오인할 수 있음 — 빌드 실패 시엔 결과 디렉터리를 비우고 다시 돌릴 것

## 2026-09-19 (이어서, Spring Batch 6 removal 예정 API 대체 — 이슈 #66)
### 한 일
- 5개 도메인 주간 집계 배치가 공유하던 removal 예정 API를 대체 API로 일괄 전환: `JobLauncher` → `JobOperator.start(job, params)`(JobOperator가 JobLauncher를 상속, `@EnableBatchProcessing`이 이미 빈 제공), `StepBuilder.chunk(int, PlatformTransactionManager)` → `chunk(int)` + `.transactionManager(...)`(새 `ChunkOrientedStepBuilder`), 테스트의 `JobLauncherTestUtils`/`launchJob` → `JobOperatorTestUtils`/`startJob`
- 대체 API는 문서 대신 실제 jar(`javap`)로 확인 — `JobOperatorTestUtils`가 `JobLauncherTestUtils`를 상속하고, `ChunkOrientedStepBuilder`가 reader/processor/writer/transactionManager를 그대로 받는 것을 확인
- 컴파일 경고에서 removal/deprecated 전부 제거. `./gradlew :api:test :common:test` 278개 전체 통과. 새 스텝 빌더가 청크 트랜잭션을 유지하는지는 지연 로딩을 쓰는 meal 배치 테스트가 잡아줌
- 실제 docker로 5개 Job을 모두 실행해 psql 확인(life 3/2, study 3/95, health 71/7, pknu 3/2, meal 3일 평균 1000), 데이터 추가 후 재실행 시 같은 행 갱신 확인

### 막힌 것
- life/study/pknu Job이 COMPLETED인데 통계 행 0건 — 전환 회귀를 의심하고 멈춤
→ 원인: 회귀가 아니라 시드 데이터가 안 들어간 검증 스크립트 오류. zsh는 따옴표 없는 변수를 단어 분리하지 않아 `set -- $d`가 값을 나누지 못했고 JSON이 깨졌는데, 시드 응답을 `/dev/null`로 버려 몰랐음. DB 원본 행 수 0건으로 확인
→ 해결: 시드 응답을 출력하고 배치 전에 원본 행 수를 확인하는 절차로 재검증 — 기대값과 일치
- 같은 스크립트의 `for path in ...`가 zsh 특수 변수 `path`(PATH와 연동)를 덮어써 curl/python3/sed/pkill이 전부 사라짐 → 변수명 변경, 이 동안 남은 앱/DB를 이어서 정리

### 배운 것
- "COMPLETED인데 0건"은 이슈 #62에서 겪은 함정의 재발 — 배치 성공 여부가 아니라 원본 행 수와 기대 집계값을 먼저 적어두고 대조해야 함. 검증 스크립트가 응답을 버리면 이런 실수를 못 잡음
- zsh에서는 `path`/`status` 같은 특수 변수명과 `set -- $var` 단어 분리에 의존하지 말 것
- 시작 시 `ItemReader is an interface` 경고 10개는 전환 전후 동일(10 → 10)해서 회귀가 아님을 로그 비교로 확인
