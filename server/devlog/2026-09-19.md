## 2026-09-19 (주간 집계 배치를 health 도메인으로 확장 — 이슈 #61)
### 한 일
- 이슈 #58 진행 상황을 점검: life(#54)·study(#60)는 머지 완료, health(#61)·pknu(#62)가 남아있어 health부터 착수
- `HealthLogWeeklyStat`(주간 로그 수/평균 체중/평균 수면) + Flyway V21, `analytics/health`(Job/Step/Reader/Processor/Writer, BatchService), 컨트롤러(GET 조회 + POST 수동 배치 트리거), 스케줄러 등록
- HealthLog는 부모 엔티티 없이 전역 로그라 Reader의 처리 단위를 "대상 주(LocalDate)"로 삼음 — 그 주에 로그가 없으면 Reader가 비어 통계 행이 생기지 않음
- 이슈에서 짚어둔 null 처리: JPQL `AVG`가 null을 무시하고, 값이 전혀 없으면 null을 반환하므로 그대로 nullable 컬럼에 저장(0으로 채우지 않음)
- `./gradlew :api:test` 220개 전체 통과. 실제 `docker compose up`(Postgres+Kafka)+`bootRun`으로 대상 주 3건(1건은 체중/수면 null)+주 밖 2건 → `logCount=3, avgWeight=71, avgSleep=7`, 로그 1건 추가 후 재실행 시 같은 행이 `logCount=4, avgWeight=72`로 갱신, 로그 없는 주는 행 미생성, 잘못된 날짜는 400을 curl로 확인. `psql`로 통계 행과 `batch_job_execution` 3건(COMPLETED)이 실제로 영속화된 것도 직접 확인

### 막힌 것
- `FlywayMigrationIntegrationTest`가 마이그레이션 개수를 20으로 하드코딩해 V21 추가 즉시 실패
→ 원인: 마이그레이션이 늘 때마다 손으로 고쳐야 하는 매직 넘버
→ 해결: 21로 갱신하고 새 테이블도 expectedTables에 추가. pknu(V22)에서도 같은 갱신이 필요함

### 배운 것
- 부모 엔티티가 없는 도메인은 Reader의 처리 단위를 "부모 ID"에서 "대상 주"로 바꾸면 같은 Reader-Processor-Writer 패턴을 그대로 쓸 수 있음
- 실환경 검증 시 API에 `X-API-KEY` 헤더(기본값 `dev-local-key`)가 필요 — 헤더 없이 curl하면 전부 401이라 처음에 검증이 헛돌았음

## 2026-09-19 (이어서, 주간 집계 배치를 pknu 도메인으로 확장 — 이슈 #62)
### 한 일
- health(#61, PR #64) 머지 직후 이어서 pknu(Assignment) 진행 — 이걸로 이슈 #58의 하위 이슈 3개(study/health/pknu)가 전부 완료됨
- `AssignmentWeeklyStat`(주간 총 과제 수/완료 수, `dueDate` 기준) + Flyway V22, `analytics/pknu`(Job/Step/Reader/Processor/Writer, BatchService), 컨트롤러(GET 조회 + POST 수동 배치 트리거), 스케줄러 등록
- Reader는 대상 주에 마감인 과제가 있는 courseId만 선별, 응답에는 파생값 `completionRate`(완료 수/총 수)를 포함(저장은 카운트만)
- `./gradlew :api:test` 223개 전체 통과. 실제 docker+bootRun에서 코스1(대상 주 3건 중 2건 완료, 주 밖 2건 제외) → `3/2`, 코스2 → `1/0`, 과제 완료 처리+추가 후 재실행 시 같은 행이 `4/3`(completionRate 0.75)로 갱신, 마감 과제 없는 주는 행 미생성을 curl과 `psql`로 확인

### 막힌 것
- 실환경 검증 첫 시도에서 코스 생성 요청이 전부 400이라, 배치는 COMPLETED인데 통계 행은 0건이었음
→ 원인: 시드 요청에 `credits`로 잘못 보냄(실제 필드명은 `credit`) — 기능 버그가 아니라 검증 데이터 오류. 코스가 없으니 배치가 빈 Reader로 정상 종료해 "성공"처럼 보였음
→ 해결: 필드명 수정 후 재시드·재검증

### 배운 것
- 배치가 COMPLETED여도 처리 대상이 0건이면 아무것도 검증되지 않은 것 — 기대 집계값(total/completed)을 먼저 적어두고 실제 DB 행과 대조해야 함
- 새 도메인을 이 패턴으로 복제할 때 sed 치환은 대소문자 변형(`findByTopicId` vs `topicId`)을 놓치기 쉬움 — 치환 후 원본 도메인 용어가 남았는지 grep으로 확인해야 함
