## 2026-09-21 (Jenkinsfile 작성 및 로컬 Jenkins 컨테이너로 파이프라인 검증 — 이슈 #82, 상위 #55)
### 한 일
- 사용자 결정 반영: 이미지 저장소는 GHCR, Jenkins는 k3s와 같은 서버의 Docker 컨테이너, iOS 클라이언트는 이 레포의 `client/`, 노드 밖 백업(#80)은 보류
- `Jenkinsfile`(테스트 → 이미지 빌드 → GHCR push → k3s 배포 → 롤아웃 확인, 실패 시 `rollout undo`)과 Jenkins 이미지(`ci/jenkins/Dockerfile`: JDK 17 + docker CLI + kubectl + 플러그인), 서버 구성 문서(`ci/README.md`) 작성
- Jenkinsfile을 문법 검증만 하지 않고 **실제로 실행**: 로컬 Jenkins 컨테이너 + 로컬 레지스트리(GHCR 대체) + 일회용 k3s(실제 서버 대체)에서 빌드 #2가 처음부터 끝까지 SUCCESS — 테스트 → 이미지 빌드(4m57s) → push(`2-0fba489`) → 배포 → `deployment "hubdash-api" successfully rolled out`, 배포된 앱은 새 이미지로 `restarts=0`, 갱신 배포 경로까지 확인
- 실패 경로 검증: 존재하지 않는 이미지로 배포하면 `ErrImagePull`로 롤아웃이 실패하고 `rollout undo`로 직전 이미지가 복구되어 API가 다시 200. 빌드 로그에 토큰/kubeconfig 인증서/시크릿 값 노출 0건(마스킹 확인). 선언형 린터가 잘못된 Jenkinsfile을 실제로 거부하는 것도 확인해 "통과"가 공허하지 않음을 증명
- 검증 후 컨테이너/네트워크/이미지/이번 세션의 볼륨 7개를 정리(이전 세션의 볼륨 24개는 건드리지 않음)

### 막힌 것
- 파이프라인을 실제로 돌려서야 나온 문제 세 가지
  1. **Testcontainers가 Jenkins 컨테이너 안에서 실패** — `Can not connect to Ryuk at 172.17.0.1:50566`. docker 소켓을 마운트한 컨테이너는 호스트 데몬에 컨테이너를 띄우므로 게시 포트가 이 컨테이너가 아니라 호스트에서 열리는데, Testcontainers의 기본 추정(브리지 게이트웨이)이 Docker Desktop에서는 맞지 않음 → 이미지에 `TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal`을 넣고, 리눅스에서는 `--add-host`가 필요함을 문서화
  2. **롤아웃 300초 초과** — 새 클러스터가 `postgres:16`을 처음 받는 데만 4분 54초. 파이프라인은 올바르게 실패했고 `rollout undo` 훅도 실행됐으나(첫 배포라 되돌릴 리비전 없음), 제한을 600초로 늘림
  3. **앱이 Kafka보다 먼저 떠서 2번 재시작** — 앞선 콜드 스타트 검증에서는 이미지가 캐시되어 있어 드러나지 않았던 경합. `Failed to construct kafka consumer`, 원인 확인 후 initContainer를 `wait-for-dependencies`(pg_isready + Kafka 포트 접속)로 확장하고, Kafka를 일부러 내린 채 배포해 `Init:0/1`로 기다리다 복구 후 `restarts=0`으로 뜨는 것을 확인
- 검증 환경의 함정들(파이프라인 자체 문제가 아님): macOS의 AirPlay가 5000 포트를 사용해 레지스트리를 5001로 변경, Jenkins git 플러그인이 로컬 `file://` 저장소 체크아웃을 기본 차단해 허용 플래그를 켬
- 내 검증 스크립트 오류 — 변수에 명령을 담아 `$K get ...`으로 실행했다가 zsh가 단어 분리를 하지 않아 `command not found`(이번 세션 네 번째 같은 함정), `kubectl delete deployment X sts/Y` 잘못된 문법의 오류를 `2>/dev/null`로 버려 실패를 못 봄, `docker volume rm $MINE`이 같은 원인으로 실패했고 출력 문구를 하드코딩해 "모두 09-16~17 생성"이라는 사실과 다른 내용을 출력함 → 함수/반복문으로 바꾸고 결과는 실제 값으로만 출력

### 배운 것
- 문법 검증과 실행 검증은 다르다 — 린터는 통과했지만 실제 실행에서 Testcontainers 네트워킹, 콜드 이미지 풀 시간, Kafka 기동 경합 세 가지가 나왔음. CI 파이프라인은 가능하면 일회용 환경에서 끝까지 돌려봐야 함
- 이미 캐시가 있는 클러스터에서의 검증은 콜드 스타트 문제를 가림 — 이미지 풀 시간이 서비스마다 달라지는 상황이 실제 경합을 만듦
- 검증 도구의 "통과"는 도구가 실제로 실패도 잡는지 함께 확인해야 의미가 있음(린터에 고의로 깨뜨린 파일을 넣어 확인)
- 에러 출력을 `/dev/null`로 버리는 습관이 실패를 성공처럼 보이게 함 — 이번 세션에서 반복된 원인. 출력 문구를 미리 하드코딩하지 말고 실제 값을 출력할 것
- Gradle `UP-TO-DATE` 때문에 입력이 바뀌지 않은 커밋의 Test 단계는 3초 만에 끝남 — 정상 동작이지만 처음 보면 테스트가 안 돈 것처럼 보여서 문서에 적어둠

## 2026-09-21 (이어서, iOS/Mac 클라이언트 결정 확정 및 API 클라이언트 패키지 — 이슈 #84, 상위 #57)
### 한 일
- 사용자 결정 반영: 클라이언트는 이 레포의 `client/`. 스택은 SwiftUI(iOS + macOS)이고 핵심 로직을 Swift Package `HubDashKit`에 두어 화면 없이 `swift build`/`swift test`로 검증
- 개발 환경 확인: Xcode 앱이 없고 Command Line Tools만 있어 iOS SDK/시뮬레이터/`xcodebuild`를 쓸 수 없음 → 화면 앱은 제외하고 검증 가능한 API 층까지만 구현, 화면/Xcode 프로젝트는 후속 이슈(#85~#88)로 분리
- `HubDashKit` 구현: `APIClient`(X-API-KEY, 봉투 해석, 전송 계층 분리), `APIError`(401/서버 오류/비JSON 응답/모델 불일치/네트워크 5종 구분), `LocalDate`/`LocalDateTime` 코덱, 식단 도메인(끼니, 음식 항목, 하루 합계) 모델과 API
- 단위 테스트 28개(스텁 전송 계층, 실제 서버 응답 형태의 샘플) + **계약 테스트 9개**(실제 서버에 붙어 Swift 모델이 진짜 응답을 디코딩하는지 확인, 환경변수가 없으면 건너뜀). 실제 서버(docker + bootRun)에서 37개 전부 통과, 연속 3회 실행도 통과
- 계약 테스트가 정말 어긋남을 잡는지 변이로 확인: 열거형 값을 `LUNCH` → `LUNCHX`로 틀리게 바꾸자 요청 방향(서버가 400 "요청 본문을 읽을 수 없습니다"으로 거부)과 응답 방향(`data.meals.Index 1.mealType` 위치까지 짚는 디코딩 오류) 양쪽에서 실패, 원상복구 후 37개 통과

### 막힌 것
- 첫 `swift test`가 `error: fatalError`로 끝남 — 원인은 툴체인이 아니라 `Package.swift`에 `platforms`가 없어 SwiftPM이 macOS 10.13을 기본으로 잡는데 swift-testing 매크로는 10.15 이상을 요구하는 것. `platforms`를 명시해 해결하고, 일부러 틀린 검증이 `✘`로 정확히 보고되는 것까지 확인해 테스트 도구를 신뢰할 수 있음을 먼저 확인
- 첫 변이 검증이 의도와 달랐음 — 필드 이름(`name` → `title`)을 바꿨더니 테스트 코드가 `.name`을 참조해 컴파일 단계에서 실패했고, 계약 테스트의 디코딩까지 도달하지 못함. 컴파일은 되지만 실제 응답과 어긋나는 변이(열거형 원시값)로 바꿔 다시 확인. 그 뒤에도 `head`로 출력을 잘라 계약 테스트 자체의 실패가 안 보였던 것을 `--filter`로 계약 스위트만 돌려 확인
- 변이로 계약 테스트가 중간에 중단되어 서버에 끼니가 남았고, 고정 날짜(2001-03-05)를 쓰는 테스트가 잔재와 연속 실행에 취약함을 발견 → 매 실행마다 무작위 먼 과거 날짜를 쓰도록 바꾸고 같은 서버에 연속 3회 통과 확인
- 테스트에 의미 없이 뒤엉킨 표현식을 급하게 써 넣었다가 실행 개수를 확인하는 과정에서 발견해 정리

### 배운 것
- 검증 도구가 실패를 잡는지(틀린 검증이 `✘`로 나오는지)를 먼저 확인해야 "통과"가 의미 있음 — 계약 테스트도 변이로 실패를 유도해 봐야 함. 변이는 컴파일 단계에서 걸리지 않고 실제 검증 지점까지 도달하는 형태로 골라야 함
- 서버 `LocalDateTime`은 시간대가 없고 소수 초 자릿수가 가변(Jackson이 끝의 0을 생략)이라 `Date` 기반 기본 디코더로는 안 됨 — 실제 서버 응답을 받아보고서야 알 수 있는 사실. 달력 날짜는 `Date`가 아니라 별도 타입으로 다뤄야 시간대에 따라 하루가 밀리지 않음
- 스텁 단위 테스트는 서버가 바뀌어도 통과하므로 클라이언트-서버 계약은 실제 서버를 대상으로 한 테스트가 있어야 지킬 수 있음
- 건너뛴 테스트가 통과로 세어지지 않는지(`skipped`로 표시되는지)와 실제로 실행된 개수(37 = 단위 28 + 계약 9)를 함께 확인해야 함
