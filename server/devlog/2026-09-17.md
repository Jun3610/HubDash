→ 원인: 최초 설계에 멱등성 가드가 없었음
→ 해결: 상태가 PENDING이 아니면 건너뛰는 가드 추가, 컨슈머 직접 재호출로 재전달 시나리오를 시뮬레이션하는 테스트 작성

### 배운 것
- 이 프로젝트가 쓰는 Spring Boot 4.x는 기능별 자동설정을 `spring-boot-autoconfigure` 모노리스에서 계속 분리해나가는 추세다(webmvc-test, jpa-test에 이어 kafka도) — 새 스타터를 추가할 때는 "라이브러리 자체" 의존성이 아니라 반드시 `org.springframework.boot:spring-boot-starter-*` 형태의 정식 스타터가 있는지 먼저 확인해야 한다
- Kafka Consumer 설계에서 "검증 실패=비즈니스 실패"와 "일시적 장애"를 구분하는 것만큼이나, "정상 처리 완료 후 재전달"에 대한 멱등성도 처음부터 설계에 넣어야 한다 — at-least-once 전달 보장은 예외 처리 전략과 별개로 항상 따라오는 제약이라, 상태 기계(PENDING/PROCESSED/FAILED)가 있는 Consumer는 그 상태를 가드 조건으로 재사용하면 비용 없이 멱등성을 얻을 수 있었다
- `FlywayMigrationIntegrationTest`처럼 마이그레이션 개수/테이블 목록을 하드코딩한 테스트는 새 도메인/파일럿을 추가할 때마다 반드시 같이 갱신해야 하는 체크리스트 항목으로 굳어졌다 — 계획서 Known Pitfalls에 명시해두고 시작하니 놓치지 않았음

### 막힌 것
- 최초 설계한 `RawMemoRequest`에 `titleRaw`/`contentRaw`의 길이 상한이 없었음 — "raw는 검증 안 한다"는 컨셉을 과하게 적용해서, `memo_raw` 컬럼(200/5000자) 폭을 넘는 값이 오면 Kafka 발행 이전에 DB 저장 자체가 깨질 뻔한 걸 구현 중 직접 발견
→ 원인: health/schedule은 "raw여도 저장소 컬럼 폭만큼은 방어"하는 걸 이미 하고 있었는데(RawEventRequest의 @Size), 그 사실을 처음에 놓치고 memo만 형식 검증을 통째로 생략함
→ 해결: RawMemoRequest에 컬럼 폭과 동일한 @Size(200/5000) 추가. 커밋하기 전에 코드 재검토 중 발견해서 별도 수정 커밋 없이 반영
- memo는 blank/필수 여부 외에 검증할 "의미적 규칙"(숫자 범위, 날짜 비교, FK 존재 등)이 없어서, Consumer의 blank/길이 체크가 DTO 레벨 검증(@NotBlank/@Size)과 완전히 중복됨 — 정상 API 경로로는 이 분기를 절대 탈 수 없어서, 통합 테스트에서 Repository로 직접 저장(DTO 우회)해 Consumer 로직만 따로 검증해야 했음
→ 원인: memo 자체가 이 프로젝트에서 가장 단순한 엔티티라 ETL 단계의 "부가가치"가 구조적으로 얕음
→ 해결: 그래도 Consumer가 producer(DTO)를 신뢰하지 않고 자체 재검증한다는 설계 원칙은 동일하게 유지(방어적 프로그래밍) — 다만 테스트는 API 경유가 아니라 Repository 직접 저장으로 그 경로를 인위적으로 열어야 했음

### 배운 것
- 도메인마다 "raw→ETL"의 실질적 가치가 다르다 — health/schedule은 숫자범위/날짜비교 같은 진짜 의미적 검증이 있어 ETL 계층이 뚜렷한 역할을 하지만, memo처럼 필수/길이 검증뿐인 도메인은 Consumer의 재검증이 DTO와 중복되는 게 당연하다. 그래도 "producer를 신뢰하지 않는다"는 방어적 설계 원칙 자체는 도메인 복잡도와 무관하게 일관되게 유지하는 게 맞다고 판단
- "raw는 검증 안 한다"를 형식 검증(길이/필수)과 의미 검증(범위/관계/존재)으로 나눠서 생각해야 한다 — 형식 검증(특히 저장소 컬럼 폭 방어)은 raw 단계에서도 필요하고, ETL이 진짜로 담당하는 건 의미 검증뿐이다. 이 구분을 명시적으로 인지하지 못하면 다음 도메인(hub/study/life/pknu)에서도 같은 실수(저장소 폭 방어 누락)가 반복될 수 있음 — 이후 도메인 작업 시 RawXRequest 설계 단계에서 항상 "컬럼 폭 방어"부터 먼저 체크할 것

### 막힌 것
- 실제 `bootRun` 검증 중 `POST .../batch-runs`가 매번 `jobExecutionId=1`을 반환하고, `docker exec ... psql`로 `batch_job_execution`을 직접 조회하면 항상 0건이었음(Job은 COMPLETED로 정상 동작하는데도) — HTTP 응답만 보면 "성공"처럼 보였지만 실제 DB를 직접 들여다보고서야 발견한 문제
→ 원인: `spring-boot-batch` 4.1.1의 `BatchAutoConfiguration`이 문서에 명시된 대로 "in-memory 저장소"만 제공한다(`DefaultBatchConfiguration.jobRepository()`가 `ResourcelessJobRepository`로 하드코딩됨) — Boot 3.x까지 있었던 "DataSource가 있으면 자동으로 JDBC JobRepository를 쓴다"는 동작이 Spring Batch 6.0에서 사라짐. Job 실행 자체는 문제없이 되니 겉으로는 정상처럼 보이는 게 함정이었음
→ 해결: `@EnableBatchProcessing`+`@EnableJdbcJobRepository`(Spring Batch 6.0 신규)를 직접 선언한 `pipeline/config/BatchConfig`를 추가해 Boot의 in-memory 기본값을 무효화. 기본 `dataSourceRef`/`transactionManagerRef`("dataSource"/"transactionManager")가 이 앱의 실제 빈 이름과 일치해 별도 지정 없이 바로 Postgres로 연결됨 — 재기동 후에도 실행 이력이 이어지는 것(jobExecutionId가 1→2→3으로 계속 증가)까지 직접 확인
- 위 수정 직후 테스트가 3개 실패(H2에 `BATCH_JOB_INSTANCE` 테이블 없음) → 78개 실패(여러 스프링 컨텍스트가 같은 H2 in-memory DB를 공유해 스키마 스크립트를 두 번 실행하며 "테이블이 이미 있음"으로 충돌)로 연쇄적으로 악화
→ 원인: `@EnableJdbcJobRepository`로 전환하면서 Boot 자체의 `spring.batch.jdbc.initialize-schema`(Boot의 BatchAutoConfiguration에만 연결된 프로퍼티)가 더 이상 아무 효과가 없어졌고, 테스트 H2는 Flyway도 꺼둬서(V18 미적용) 배치 스키마를 만들 방법이 없었음. 첫 대응으로 spring-batch-core jar의 원본 `schema-h2.sql`을 `spring.sql.init`으로 직접 적용했지만, 그 스크립트는 재실행을 가정하지 않은 순수 `CREATE TABLE`이라 컨텍스트가 여러 번 만들어지는 테스트 스위트에서 충돌함
→ 해결: 원본을 수정하는 대신 `CREATE TABLE IF NOT EXISTS`/`CREATE SEQUENCE IF NOT EXISTS`로 바꾼 테스트 전용 사본(`schema-h2-batch.sql`)을 만들어 몇 번이 실행되어도 안전하게 함

### 배운 것
- HTTP 응답이 "성공"이어도 그게 진짜 영속화까지 증명하지는 않는다 — Job/Step 실행 자체는 정상 작동해서 API 레벨 검증만으로는 절대 못 잡는 버그였고, `docker exec ... psql`로 실제 테이블을 직접 들여다본 게 발견의 핵심이었다. 이번 경험을 계기로 hubdash-workflow 스킬에 "실제 docker 환경에서 검증하고, DB까지 직접 확인하라"는 규칙(Rule 3)을 새로 추가함
- 메이저 버전이 올라간 라이브러리는 "그냥 예전처럼 동작하겠지"라고 가정하면 안 된다 — Spring Batch 5→6에서 `DefaultBatchConfiguration`의 기본 동작 자체(JDBC 자동 연결 여부)가 바뀌었는데, 컴파일도 되고 Job도 정상 실행되니 한동안 눈치채기 어려웠다. 이 프로젝트가 최신 프리뷰 버전의 Boot/Batch를 쓰는 한, "동작한다"와 "의도한 대로 동작한다"를 구분해서 항상 실제 인프라로 재확인해야 한다
- 여러 스프링 테스트 컨텍스트가 같은 H2 in-memory DB URL을 공유할 수 있다는 전제 위에서, 프레임워크가 제공하는 원본 스키마 스크립트를 그대로 재사용하기보다 재실행 안전성(`IF NOT EXISTS`)을 직접 보장하는 사본을 두는 편이 이 프로젝트의 테스트 구조와 더 잘 맞는다
