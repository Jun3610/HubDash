### 막힌 것
- `org.springframework.kafka:spring-kafka`만 추가했더니 `KafkaTemplate` 빈이 전혀 생성되지 않아 전체 컨텍스트 테스트가 `NoSuchBeanDefinitionException`으로 실패
→ 원인: Spring Boot 4.x가 Kafka 자동설정을 `spring-boot-autoconfigure`에서 분리해 별도 모듈(`spring-boot-kafka`)로 옮김 — 이미 겪은 webmvc/jpa test-autoconfigure 패키지 분리와 같은 패턴. `spring-kafka`는 순수 통합 라이브러리일 뿐 Boot 자동설정을 포함하지 않음
→ 해결: `org.springframework.boot:spring-boot-starter-kafka`(BOM에 등록된 정식 스타터)로 교체
- 테스트 프로파일에서 Kafka 자동설정 자체를 껐더니(`spring.autoconfigure.exclude`) 이번엔 `KafkaTemplate`을 주입받는 `RawHealthLogService`를 포함한 전체 컨텍스트 테스트가 같은 예외로 다시 실패
→ 원인: 빈을 아예 없애면 그 빈을 의존하는 다른 빈의 생성 자체가 막힘
→ 해결: 빈은 그대로 두고 `spring.kafka.listener.auto-startup=false`로 리스너 컨테이너의 자동 시작만 꺼서, 존재하지 않는 브로커에 연결 시도는 안 하면서 `KafkaTemplate` 빈 자체는 정상 주입되게 함. `@EmbeddedKafka`를 쓰는 테스트에서만 이 프로퍼티와 `bootstrap-servers`를 오버라이드
- 자체 리뷰 중 Kafka가 at-least-once 전달을 보장한다는 점에서, 크래시/리밸런싱으로 같은 이벤트가 재전달되면 이미 PROCESSED/FAILED인 레코드를 Consumer가 다시 처리해 `HealthLog`가 중복 생성될 수 있다는 걸 발견
→ 원인: 최초 설계에 멱등성 가드가 없었음
→ 해결: 상태가 PENDING이 아니면 건너뛰는 가드 추가, 컨슈머 직접 재호출로 재전달 시나리오를 시뮬레이션하는 테스트 작성

### 배운 것
- 이 프로젝트가 쓰는 Spring Boot 4.x는 기능별 자동설정을 `spring-boot-autoconfigure` 모노리스에서 계속 분리해나가는 추세다(webmvc-test, jpa-test에 이어 kafka도) — 새 스타터를 추가할 때는 "라이브러리 자체" 의존성이 아니라 반드시 `org.springframework.boot:spring-boot-starter-*` 형태의 정식 스타터가 있는지 먼저 확인해야 한다
- Kafka Consumer 설계에서 "검증 실패=비즈니스 실패"와 "일시적 장애"를 구분하는 것만큼이나, "정상 처리 완료 후 재전달"에 대한 멱등성도 처음부터 설계에 넣어야 한다 — at-least-once 전달 보장은 예외 처리 전략과 별개로 항상 따라오는 제약이라, 상태 기계(PENDING/PROCESSED/FAILED)가 있는 Consumer는 그 상태를 가드 조건으로 재사용하면 비용 없이 멱등성을 얻을 수 있었다
- `FlywayMigrationIntegrationTest`처럼 마이그레이션 개수/테이블 목록을 하드코딩한 테스트는 새 도메인/파일럿을 추가할 때마다 반드시 같이 갱신해야 하는 체크리스트 항목으로 굳어졌다 — 계획서 Known Pitfalls에 명시해두고 시작하니 놓치지 않았음

- `KafkaTopicConfig`에 `SCHEDULE_RAW_EVENT_TOPIC` 추가(기존 health 토픽 옆에 이어서), `RawEventConsumerIntegrationTest` 4종(정상/날짜파싱실패/순서오류/재전달) 추가
- 실제 `docker compose up`(Postgres+Kafka)+`bootRun`으로 정상 케이스(PROCESSED+Event 1건 생성)와 실패 케이스 2종(endAt<startAt, 파싱 불가능한 날짜) 전부 curl로 직접 검증

### 막힌 것
- 새로 만든 `RawEventCreatedEvent`가 Consumer에서 전혀 소비되지 않고 raw 레코드가 계속 PENDING에 머무름 — EmbeddedKafka 테스트 4개가 전부 10초 타임아웃으로 실패, 실제 `bootRun`으로 재현 전 로컬 테스트 단계에서 먼저 발견
→ 원인: health 파일럿이 `spring.kafka.consumer.properties.spring.json.trusted.packages`를 `com.junyoung.dashboard.domain.health.event`로 좁게 설정해둠 — JacksonJsonDeserializer가 이 목록에 없는 `domain.schedule.event` 패키지의 이벤트를 신뢰하지 않고 조용히 역직렬화를 거부(에러 로그도 눈에 잘 안 띄어서 처음엔 "리스너가 아예 안 붙었나" 의심했음)
→ 해결: 신뢰 패키지를 `com.junyoung.dashboard.domain.*`로 넓혀서 이후 5개 도메인(hub/study/life/pknu/memo/reminder)을 확장할 때마다 이 설정을 매번 고칠 필요가 없게 함. 겸사겸사 도메인 특정 이름이던 consumer group-id(`hubdash-health-etl`)도 `hubdash-raw-etl`로 일반화
- `./gradlew build` 실행 중 `java_pid*.hprof`(741MB) 힙 덤프 파일이 작업 디렉토리에 생성됨 — 어느 JVM(테스트용 KRaft 브로커 인프로세스 인스턴스 중 하나로 추정)이 크래시하면서 남긴 것으로 보임
→ 원인: 정확한 원인 미확인(빌드 자체는 최종적으로 성공했고 관련 스택트레이스를 못 찾음)
→ 해결: 커밋 대상에 포함되지 않게 즉시 삭제. 재발하면 원인을 더 깊게 봐야 함 — 지금은 1회성으로 판단하고 넘어감

### 배운 것
- Kafka JSON 역직렬화 신뢰 패키지를 첫 도메인(health) 기준으로 좁게 잡아둔 게, 두 번째 도메인 확장에서 곧바로(그것도 침묵 실패로) 재발했다 — 여러 도메인이 같은 Kafka 인프라를 공유하는 구조라면 파일럿 단계에서부터 상위 패키지 와일드카드로 잡아뒀어야 했다. "파일럿이니까 좁게 시작"이 다음 확장의 함정이 될 수 있다는 걸 확인
- health 패턴을 거의 그대로 복붙 수준으로 재사용해도 인프라 설정(신뢰 패키지, group-id) 같은 "공유 자원" 쪽은 도메인별 파일이 아니라서 재사용 시 반드시 다시 점검해야 하는 지점으로 남는다
