### 막힌 것
- 실제 Postgres에 `bootRun` 했더니 `Flyway ... Migration checksum mismatch for migration version 1` 에러
→ 원인: hub 도메인 검증 때(2026-09-14) 만든 로컬 Postgres 볼륨(`server_hubdash-db-data`)에 V1__init.sql이 이미 적용돼 있었는데, 그 이후 hub 최종 리뷰에서 V1에 인덱스 한 줄을 추가하면서(커밋 132a5f5) 파일 체크섬이 바뀜 — 로컬 볼륨은 예전 체크섬을 그대로 기억하고 있어서 불일치 발생. 코드 버그가 아니라 로컬 개발용 볼륨이 낡은 것뿐
→ 해결: `docker compose down -v`로 볼륨까지 지우고 새로 `up` — 신선한 DB에 V1, V2가 정상 순서대로 적용됨 확인
- 최종 리뷰에서 이 브랜치의 핵심 목적(topicId 이동이 실제로 반영되는지)이 수동 curl 검증에만 의존하고 있고 재실행 가능한 테스트가 없다는 지적
→ 원인: 계획서 Task 9는 StudyTopic 엔드투엔드 테스트만 요구했고 StudyProgress 쪽은 통합 테스트 범위 밖이었음
→ 해결: topic A에 progress 생성 → topic B로 PUT 이동 → 응답의 topicId가 실제로 B로 바뀌었는지 확인하는 통합 테스트 추가

### 배운 것
- 로컬 개발용 Docker 볼륨은 "영속화된 상태"가 아니라 "이전 코드 상태의 스냅샷"으로 취급해야 한다 — 마이그레이션 파일을 리뷰 과정에서 수정했다면, 이미 그 파일을 적용해본 적 있는 로컬 볼륨은 체크섬이 안 맞을 수 있다는 걸 염두에 둬야 함. 실제 배포 환경이 아닌 순수 로컬 검증용 볼륨이면 `down -v`로 그냥 리셋하는 게 제일 빠름
- 이전 도메인(hub)의 "발견된 함정"을 다음 계획(study)에 반영할 때는, 그 도메인의 **최종(리뷰 반영 후) 상태**를 기준으로 삼아야 한다 — 이번에 plan을 hub의 리뷰 완료 전 테스트 세트를 참고해서 짜는 바람에, hub 최종본에는 있는 "새 부모 없음" update 테스트가 study 계획에는 빠져있었다. 최종 리뷰어가 직접 짚어준 메타 교훈
